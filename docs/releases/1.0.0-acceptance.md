# MoneyPal 1.0.0 发布验收记录

此模板只记录版本、命令、环境与结果；不得写入账本内容、用户路径、账户名或交易说明。每个平台均从 registry 的 `next` 标签安装两个包，使用临时验收账本执行显式 `setup-runtime`、初始化、校验、查询、预览、确认提交和卸载后的账本哈希比对。

## 发布流程

MoneyPal 按一个产品管理版本，一次发布生成 `dsh-moneypal` 与 `mcp-moneypal` 两个包。流程由 Release Please 与一个发布工作流驱动：

1. 功能 PR 通过 Test 后以 squash 方式合并到 `main`，提交标题取 PR 标题。
2. `main` push 触发 Release 工作流运行 Release Please，自动维护 Release PR；这一步不发布。
3. 维护者关闭再重新打开 Release PR 触发 Test，`GITHUB_TOKEN` 创建的 PR 不会自动触发工作流；机器人更新 PR 后要对最新提交重复该操作。
4. Test 通过后合并 Release PR，Release Please 创建 `v<版本>` tag 与 GitHub Release（RC 标记为 Prerelease）。
5. Release 工作流从该版本 SHA 重新构建、运行门禁并保留已验收的 tgz，然后按 DSH、MCP 顺序发布到 npm `next`。

`next` 始终由工作流写入；`latest` 保持人工提升，工作流绝不改动它。

## 发布顺序与回退

1. 运行 `npm run test:release` 与干净 checkout 中的 `npm run release:preflight`。验收记录应保存当次命令的 pass、fail、skip 数量；存在 skip 时必须说明其运行时或环境原因。
2. 合并 Release PR 后确认工作流结果：两个包都发布到 `next` 才视为成功。工作流结果就是 npm 是否成功的唯一依据，GitHub Release 只表示对应版本源码已被标记。
3. 在五个平台及真实 DSH/MCP 宿主完成下方记录；没有 registry 权限或目标平台时，运行 `npm run release:acceptance` 生成机器可读的待人工项并停止。
4. 稳定版仍先发到 `next`；两个包均完成 registry 复验、bridge 哈希与公共导出一致后，才执行 `npm run release:promote`。该命令默认 dry-run 只打印 `npm dist-tag add <pkg>@<版本> latest`；复验通过后加 `--apply` 才同时提升 `latest`，并在提升后重新核验两个包的 `latest`。两次 dist-tag 更新不是原子操作，部分失败会如实报错，需要人工核对后再重试。
5. 任一包发布或复验失败时，不提升任何 `latest`。回退是停止提升并修复后发布新的候选；不得用 npm 覆盖已发布版本，也不得触碰正式账本或共享运行时。已提升的 `latest` 可通过 `npm dist-tag add <pkg>@<旧版本> latest` 移回，但只作事故回退，不作为常规路径。

## 发布失败重试

使用 tag 重试入口，例如：

```bash
gh workflow run release.yml --ref v1.0.0-rc.4 -f tag=v1.0.0-rc.4
```

手动重试跳过 Release Please，要求运行 ref 恰好是输入 tag、tag 与对应 GitHub Release 已存在、tag 的提交在 `main` 历史中、tag 版本与根清单和 `.release-please-manifest.json` 一致，并拒绝 `1.0.0-rc.3` 及更早版本。发布脚本先检查两个包：registry 明确返回 E404 才发布；已存在且 `dist.integrity` 与本地 tgz 的 SHA-512 相同就跳过；integrity 不同或缺失则整体失败；网络、鉴权、限流和响应解析错误都当作失败，不当成 E404。

两个包的发布不是原子事务。第一包成功、第二包失败时工作流失败，按同一 tag 重试即可：已存在且字节一致的包安全跳过。若修复需要改源码或产生不同 tgz，则发布下一个候选版本，不覆盖已发布版本。Release Please 只在创建 Release 的那次返回 `release_created=true`，不要依赖“重跑旧的 run”恢复发布。

## 维护者一次性配置

1. 在 GitHub 仓库设置中允许 Actions 创建和批准 PR。
2. 合并方式使用 Squash merge，提交标题取 PR 标题。
3. 把 Test 设为 `main` 的必需检查，并要求分支为最新；不绕过 Release PR 的检查。
4. 为 `dsh-moneypal` 和 `mcp-moneypal` 分别配置 npm Trusted Publisher：owner `ding112`、repo `MoneyPal`、workflow `release.yml`、environment 留空，允许 `npm publish`。
5. 本期没有自定义 Release 附件，可以开启 Immutable Releases；它不会让 npm 发布变成原子事务。
6. 不删除或修改现有 registry 版本与 dist-tag，尤其不补发 `mcp-moneypal@1.0.0-rc.3`。

npm 使用 OIDC，工作流不读取 `NPM_TOKEN`，仓库也不需要该 secret。OIDC 的工具链要求由 Node 24 与 npm 11.14.1 满足。

## 首次上线验收

1. 合并实现 PR 后只生成 `1.0.0-rc.4` 的 Release PR，不发布 `1.0.0-rc.3`。
2. 人工关闭并重新打开该 Release PR，确认最新提交的 Test 通过。
3. 合并 Release PR。
4. 确认 `v1.0.0-rc.4`、GitHub Prerelease 与构建 SHA 一致。
5. 确认两个 npm `1.0.0-rc.4` 均存在、provenance 可用，且正常首次发布后两个包的 `next` 都是 `1.0.0-rc.4`。
6. 确认原有 `latest` 未被此次工作流改动。
7. 使用 tag 手动重试一次，确认两个包 integrity 匹配并安全跳过。

## 已知限制与阻塞

- Actions 环境无法在本地完整验证：Test 工作流可通过 PR 验证，Release 工作流只能合并后观察 Actions run，必要时用 tag 重试入口补跑。
- 双包发布不是原子事务，也没有自定义 Release 附件或 SBOM。
- `GITHUB_TOKEN` 创建的 Release PR 不会触发其他工作流，必须人工关闭再重新打开；机器人更新 PR 后要重复该操作。
- 本环境没有 npm registry 写入凭证，五平台 registry 安装验收无法在 agent 侧执行。
- 当前机器仅为 macOS arm64；macOS x64、Linux x64、Windows x64/arm64 需目标平台或 CI。
- 本机未配置真实 MCP 宿主；DSH Web 宿主已存在，但以注册表 RC 安装的实机验收需在 RC 发布后进行，且会改动宿主配置，由人工执行。
- 本地已有 MoneyPal 托管运行时（Beancount/beanquery 就绪），可直接支撑后续流程的 `setup-runtime` 与查询验证。
- 已有真实 Python 运行时测试若因环境缺失而 skip，必须在记录中写明原因，不能据此宣称完成五平台验收。
- 当前分支的 `npm run test:fast` 与 `npm test` 只执行 `build:base`，因此不生成 `dist/packages`；`install-preset` 用例导入发布包的 `dist/packages/dsh-moneypal/dist/src/install-preset.js`，已按测试分层标准移入发布层 `test:release:built`。
